## 完了した作業

### 1. フロントエンド規約違反を一括修正（#240 → PR #241）

**widget.css / themes/default.css — ハードコードカラーを CSS 変数に統一**

| 箇所 | before | after |
|---|---|---|
| ランチャー・CTA・送信ボタン・ユーザーバブルの文字色 | `#fff` | `var(--nc-color-on-primary)` |
| エラーメッセージ色 | `#b91c1c` | `var(--nc-color-error)` |
| アバター・バブル背景の color-mix 基色 | `white` | `var(--nc-color-surface)` |

`--nc-color-on-primary` と `--nc-color-error` を `default.css` に新規追加。  
ダークテーマ切り替え時に `color-mix` の基色が白固定だった問題を `--nc-color-surface` に統一して解消。

**api-client — raw `fetch()` → `fetchJson()` に統一**

- `account.ts`: `changeAdminPassword()`, `changeAdminEmail()`
- `documents.ts`: `deleteDocument()`
- `notifications.ts`: `getNotificationSettings()`, `updateNotificationSettings()`, `sendTestMail()`

全6関数のエラーハンドリングを `fetchJson()` の `ProblemDetails` パーサーに委譲し、重複した try/catch を排除。

**その他**

- `App.tsx` フッターの `AYANE` / `All rights reserved.` ハードコード文字列を `Msg.admin.footer.copyright` キーに置換（i18n 済み）
- `NotificationsPanel.tsx` の `useState('NeNe Corpus')` デフォルト値削除（サーバー取得値で上書きされるため不要）

### 2. 単体テスト網羅的追加（#242 → PR #243）

敵対的視点で「壊れやすい箇所」を優先し、PHPUnit 13 / SQLite in-memory DB を使った単体テストを 11 ファイル追加。  
テスト総数: **146 → 280**（990 アサーション）

| ファイル | テスト数 | 主な検証内容 |
|---|---|---|
| `AdminAuth/AdminPasswordResetTest` | 8 | `isExpired()` / `isUsed()` の境界値・複合状態（純粋エンティティ） |
| `AdminAuth/ChangeAdminPasswordUseCaseTest` | 10 | パスワード変更フロー・誤パスワード攻撃（DB 書き換えなし確認） |
| `AdminAuth/ChangeAdminEmailUseCaseTest` | 16 | 無効メール形式 8 種 DataProvider・重複メール・有効な境界値 |
| `AdminAuth/ConfirmPasswordResetUseCaseTest` | 9 | トークン期限切れ・使用済み・空トークン・短パスワード（DB 前チェック） |
| `AdminAuth/RequestPasswordResetUseCaseTest` | 7 | アカウント列挙防止・SMTP 未設定時のトークン保存なし・SHA-256 ハッシュ確認 |
| `Chat/SendChatMessageUseCaseEdgeCaseTest` | 14 | 会話履歴構築（current メッセージ除外）・トークン追跡・文字数制限境界 |
| `ChatLimits/ChatLimitsValidatorTest` | 18 | 型エラー（float/bool/配列）・全 8 フィールド同時エラー収集・DataProvider |
| `ChatLimits/PdoChatTokenTrackerTest` | 11 | ウィンドウ期限切れ後 peek=0・track でリセット（加算されない） |
| `ChatSettings/ChatSettingsValidatorTest` | 19 | 境界値（4000/4001字）・マルチバイト・ホワイトスペースのみ→null |
| `Settings/LlmSettingsValidatorTest` | 28 | API キー長境界（19/20字）・max_tokens クランプ動作・非数値文字列の扱い |
| `Search/SearchChunksUseCaseTest` | +6 | 空文字列・limit=0 → 1 補正・負 limit・クエリトリミング |

**テスト実施で発見・明文化した仕様:**

- `LlmSettingsValidator`: `max_tokens = 'not-a-number'` は例外を投げず `1` にクランプされる（暗黙仕様の文書化）
- `ConfirmPasswordResetUseCase`: パスワード長チェックが DB 参照より先に実行される（最適化の保護）
- `RequestPasswordResetUseCase`: 存在しないメールと既知メールで外から区別不可能な挙動（アカウント列挙防止の担保）

## 課題・気づき

| 項目 | 内容 |
|---|---|
| **PHPUnit 13 の strict な Mock/Stub 分離** | `createMock()` に `expects()` なしで使うと Notice が出る。`createStub()` を使い分ける必要がある（PHPUnit 10 以前から移行したコードで潜在的に残っている可能性） |
| **fetchOne() の null safety** | `array<string, mixed>\|null` を返すため PHPStan level 8 では `assertNotNull()` が必須。本番コードでも未チェックのまま使っている箇所がないか確認の余地あり |
| **Ingestion / HTTP ハンドラー層のテスト** | 今回はユースケース・バリデーター・リポジトリ層を優先。Ingestion パイプラインと HTTP ハンドラーはインテグレーションテストの性格が強く、別途検討が必要 |

## 所感

今日は「新機能ゼロの品質強化デー」だった。フロントエンドのハードコードカラー修正は小さい変更だが、ダークモード切り替えで意図しない白色固定が生じていた問題をきちんと塞げた。

テストは量より「何を保証するか」が大事だと改めて実感した。アカウント列挙防止やトークン保存のタイミングといった**セキュリティ上の仕様が、コードコメントではなくテストとして初めて担保された**のは今日の一番の成果。機能は実装済みでも、テストがなければ将来のリファクタで静かに壊れる可能性があった。
