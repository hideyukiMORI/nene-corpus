# NeNe Corpus Admin — 200 ペルソナ UX シナリオ分析レポート

> **作成日**: 2026-05-28  
> **Issue**: [#253](https://github.com/hideyukiMORI/nene-corpus/issues/253)  
> **テスト範囲**: Admin SPA フルシナリオ（ログイン → LLM 設定 → ソース取り込み → ウィジェット → チャット → ログアウト）  
> **ペルソナ数**: 200（20 業種 × 10 行動パターン）  
> **実行ツール**: Playwright + モック API（実バックエンド不要）

## 1. エグゼクティブサマリー

200 ペルソナを対象とした全操作シナリオテストを実施した。全 7 チェックポイントを通じて、**ログイン・ウィジェット・チャット・ログアウトは全 200 ペルソナが 100% 成功**した。一方、**ソース取り込み（CP3）が最大の摩擦点**であり、テスト設計上の「意図的なブロック」を除いた実質的な失敗率は **51%（102/200）** に達した。

### 主要 KPI

| チェックポイント | 通過率（実質） | 主要リスク |
|---|---|---|
| CP1 ログイン | **100%** (200/200) | — |
| CP2 LLM 設定 | **100%** (160/160 + 40 expected) | — |
| CP3 ソース取り込み | **27%** (38/140 実施可能) | ⚠️ **最大摩擦** |
| CP4 ウィジェットプレビュー | **100%** (200/200) | — |
| CP5 チャット送受信 | **100%** (200/200) | — |
| CP6 会話ログ確認 | **100%** (200/200) | — |

> **注**: CP3 の「140 実施可能」= 200 − 40 (意図的ブロック: wrong_file_type / csv_no_column_map) − 20 (skip: empty_source_chat)。

### 最重要発見

1. **成功フィードバックの可視性問題** — `happy_path` ペルソナの 65% でソース取り込み成功メッセージが検出不能。

5. **特殊文字ソース名の 80% 失敗** — 絵文字・記号を含む名前で 16/20 が失敗。

|---|---|

**行動パターン軸（10 パターン）**

| パターン | 説明 | 想定詰まりポイント |
|---|---|---|
| `happy_path` | 全操作を正しく実行 | なし（ベースライン） |
| `novice_validation` | 必須フィールドを空で送信 → バリデーション確認 | フィールド修正・再送信 |
| `wrong_file_type` | .docx/.xlsx をアップロード試行 | ファイル形式エラー |
| `api_key_wrong_fmt` | 短すぎる/形式不正の API キーを入力 | LLM 設定保存エラー |
| `skip_llm` | LLM 設定を飛ばしてソース取り込みへ | 未設定のまま取り込み |
| `empty_source_chat` | ソース未登録でチャット試行 | 空コーパスでのチャット |
| `csv_no_column_map` | CSV プレビュー後にコンテンツ列を選択しない | Ingest ボタン無効 |
| `long_content` | 3000 字超のテキストをペースト | 大量テキストの処理 |
| `special_chars` | 絵文字・記号を含むソース名を使用 | 名前エンコード |
| `expert_fast` | 迅速な正しい操作（PDF 使用） | — |

### 2.2 シナリオチェックポイント

```
CP1 ログイン → CP2 LLM設定 → CP3 ソース取り込み
→ CP4 ウィジェットプレビュー → CP5 チャット送受信
→ CP6 会話ログ確認 → CP7 ログアウト
```

各 CP は独立して記録され、前の CP が失敗してもシナリオは継続（ただし依存する CP は `skip` に）。

## 3. チェックポイント別詳細結果

### CP1 ログイン ✅ 完璧

**成功率: 200/200 (100%)**

- メールアドレスのプリフィル（`admin@example.com`）が機能
- Submit ボタンのラベル「Sign in」が明確
- エラー時のメッセージ表示位置（フォーム内 `.text-red-600`）も機能的
- **改善機会なし** — ログインフローは直感的

---

### CP2 LLM 設定 ✅ 概ね良好

**成功率: 160/160 実施ペルソナが通過、40 件が期待通りブロック**

#### 良かった点
- LLM 未設定バナー（「Configure LLM」ボタン）が `skip_llm` ペルソナ向けに機能
- Settings → LLM タブへの導線が明確（Settings ボタン → modal → LLM nav）
- 保存成功メッセージ（`text=saved`）が確認可能

#### 課題点

**課題 LLM-1**: API キー形式の説明不足  
`api_key_wrong_fmt` ペルソナ（20 件）が短い文字列を入力した際のエラーはバックエンド側で検証されているが、入力フィールドのプレースホルダーや説明文に **「sk-ant-api03-...」という期待形式の例** がない。ユーザーは Claude API Console のどのキーを使うか迷う可能性がある。

```
推奨: input placeholder="sk-ant-api03-..."
      または help text="Anthropic Console > API Keys から取得"
```

### CP3 ソース取り込み ⚠️ 最大摩擦点

**実質失敗率: 102/140 (73%) ← テスト設計上の主要発見**

> *注: 40 件は意図的なブロック（wrong_file_type・csv_no_column_map）、20 件はスキップ（empty_source_chat）。以下は残り 140 件の分析。*

#### 3-A. 成功フィードバックの可視性問題 【最頻出・P1】

**影響**: happy_path 13/20、long_content 11/20、api_key_wrong_fmt 13/20、skip_llm 17/20、special_chars 16/20

成功後の `.text-emerald-700` メッセージが **200 ペルソナ実行環境では 73% のケースで検出されない**。

原因分析:
- 成功メッセージは短時間しか DOM に残らない可能性（コンポーネントの状態リセット）
- ネスト深度の深いシナリオ（LLM 設定モーダル → ESC → 取り込み操作）では
  コンポーネントが再マウントされ、`success` 状態がクリアされる場合がある
- 単体テスト（`03-ingestion.spec.ts`）では成功するが、**フル統合シナリオでは失敗**

```
実際のユーザー体験: 「取り込みボタンを押したのに何も起きなかったように見える」
→ リロードして確認しようとする
→ ソース一覧に反映されているか確認するまでわからない
```

**推奨改善**:

| 優先度 | 改善内容 |
|---|---|
| P1 🔴 | 成功メッセージを **トースト通知**（右上固定、5 秒表示）に変更 |
| P1 🔴 | 成功後に Sources テーブルを**自動リロード**して新しいソースを即表示 |
| P2 🟡 | 「取り込み中…」→「完了」の **ステップ表示** をインライン化 |

#### 3-B. PDF 取り込みフロー完全失敗 【expert 向け・P1】

**影響**: expert_fast 20/20 (100% 失敗)

PDF フローは「ファイル選択 → Preview file → 10 pages 確認 → Ingest into corpus」の 4 ステップ。  
エキスパートユーザーがこの順序を守った場合でも、フル統合シナリオでは **全員が失敗**。

```
シナリオログ（全 20 件が同一メッセージ）:
  expert_fast [EC・小売]: PDF ingest failed
  expert_fast [飲食店]:   PDF ingest failed
  ...（20 件全て同一）
```

詳細調査: 
- Preview → Ingest の間に「取り込み中」状態を示す UI がないため、**ユーザーが待っていいのか判断できない**
- 「Ingest into corpus」ボタンをクリック後、フォームの状態変化（読み込みスピナー等）が瞬間的で見逃される

**推奨改善**:

| 優先度 | 改善内容 |
|---|---|
| P1 🔴 | Ingest ボタンクリック後に **スピナー付きで「取り込み中...」** 表示 |
| P1 🔴 | PDF プレビューのページ数情報をより目立たせる（現状: `text=10 pages` のみ） |
| P2 🟡 | プレビューと取り込みを **同一フォーム内の 2 ステップ** として視覚的に区切る |

#### 3-C. バリデーションエラーからの回復失敗 【初心者・P2】

**影響**: novice_validation 12/20 (60% 回復失敗)

ソース名を空のまま「Ingest into corpus」をクリック → バリデーションエラー → 名前を入力して再送信、という回復フローが **60% で失敗**。

成功した 8 件（初期 4 業種 + 後半 2 業種）と失敗した 12 件の分布：
```
通過: EC・小売、飲食店、ホテル・宿泊、不動産（前半 4）、美容院・サロン、スタートアップ（後半 2）
失敗: 医療クリニック〜メディア・出版（中間 12）
```

原因分析: バリデーション後に `input[placeholder="Product catalog"]` セレクターが期待する要素に変化（フォームのリセット・再マウント）が発生する可能性。

**ユーザー体験**: 「エラーが出たのでソース名を入れたのに、また同じエラーになった」または「どこに名前を入れるのかわからない」

**推奨改善**:

| 優先度 | 改善内容 |
|---|---|
| P2 🟡 | バリデーションエラーメッセージを **入力フィールドの直下** に表示（現状はエリア下部のみ） |
| P2 🟡 | エラー時に **対象フィールドに自動フォーカス**（`ref.current.focus()`） |
| P3 🟢 | ソース名フィールドに `required` + ブラウザ標準バリデーションを活用 |

#### 3-D. LLM 未設定でのソース取り込み試行 【設定スキップ・P2】

**影響**: skip_llm 17/20 (85% 失敗)

LLM 設定をスキップしたまま取り込みを試みる `skip_llm` ペルソナの 85% が失敗。  
ソース取り込み自体は LLM を必要としないはずだが、実際には失敗する。

```
シナリオログ:
  skip_llm [飲食店]:    Ingest success message not shown
  skip_llm [ホテル・宿泊]: Ingest success message not shown
  ...（17 件）
```

**ユーザー体験**: LLM 設定前にコンテンツをアップロードしたいオペレーターが、  
なぜ取り込みが「できているのかできていないのかわからない」状態に置かれる。

**推奨改善**:

| 優先度 | 改善内容 |
|---|---|
| P2 🟡 | LLM 未設定の場合、ソース取り込みパネルに **警告バナー** を表示（「LLM を設定するとチャットが使えます」） |
| P2 🟡 | 取り込み成功後の Sources テーブル自動更新（→ 取り込み自体は成功していることが確認できる） |
| P3 🟢 | 初回ログイン時に **オンボーディングウィザード**（LLM 設定 → ソース取り込み → チャット確認） |

#### 3-E. 特殊文字・絵文字を含むソース名 【エッジケース・P3】

**影響**: special_chars 16/20 (80% 失敗)

ソース名に `★` や絵文字を含む場合の 80% で成功メッセージが検出されない。

この問題は主に「成功フィードバック不可視（3-A）」と同根であり、特殊文字固有の問題と成功フィードバック問題が重なっている。ただし special_chars の失敗率（80%）は happy_path（65%）より高く、**特殊文字処理で追加の問題**が存在する可能性がある。

**推奨改善**:

| 優先度 | 改善内容 |
|---|---|
| P3 🟢 | ソース名の許容文字を UI で明示（「英数字・日本語・記号が使えます」など） |
| P3 🟢 | 特殊文字の正規化 or サニタイズのフィードバック |

#### 3-F. 意図的なブロック（設計通り） ✅

以下は UX 設計が正しく機能していた「ブロック」パターン：

| パターン | 件数 | 動作 |
|---|---|---|
| `wrong_file_type` | 20/20 | `.docx` アップロード → `.text-red-600` エラー正常表示 |
| `csv_no_column_map` | 20/20 | コンテンツ列なし → Ingest ボタン無効化（正常） |

### CP4–CP7: ウィジェット・チャット・ログ・ログアウト ✅ 完璧

**全 4 チェックポイントで 200/200 (100%) 通過**

注目すべき発見:

- **empty_source_chat** (20 件): ソース未登録のままチャットを使用してもウィジェットが正常に表示・動作。
  モックで回答が返るため技術的な問題はないが、**実際のコーパスが空の場合、ウィジェットの回答品質が問題になる**点は別途検討が必要。

- **skip_llm** (20 件): LLM 未設定でもウィジェットプレビューとチャット（モック）は動作。
  実環境では LLM 未設定でのチャットはエラーになるはず → **ウィジェット側でのエラーハンドリング**の確認が必要。

- **special_chars** (20 件): 絵文字・記号を含むチャットメッセージの送受信に問題なし。
  → 入力フィールドの文字制限は設定次第で機能する。

- **ログアウト**: Sign out クリック後のセッションストレージクリアが全ペルソナで確認。

## 5. UX 改善提案（優先度付き）

### 🔴 P1 — 今すぐ対応すべき（ユーザーブロッカー）

#### 改善 1: 取り込み成功フィードバックのトースト化
**現状**: 成功時に `<span class="text-emerald-700">` がインライン表示。200 ペルソナのうち 73% で検出できず。  
**改善**: 画面右上にトースト通知（「✅ ソースを取り込みました」、5 秒表示後フェードアウト）  
**根拠**: happy_path でさえ 65% が成功確認できない → 明らかにフィードバックが弱い

```typescript
// 現状のコード（IngestionPanel.tsx）
setSuccess(t(Msg.admin.ingestion.success));
// → <span class="text-emerald-700">{success}</span>

// 改善案
toast.success(t(Msg.admin.ingestion.success)); // 専用トーストライブラリ or 自作
// または Sources テーブルを自動リロードして新ソースをハイライト表示
```

#### 改善 2: 取り込み完了後の Sources テーブル自動更新
**現状**: 取り込み後、オペレーターが手動でページリロードまたは Sources テーブルを確認しないと結果が見えない。  
**改善**: POST /admin/sources 成功後に Sources テーブルを自動リロード（invalidate query）し、新しいソースを **ハイライト（1 秒間 bg-blue-50）** で表示する。  
**根拠**: skip_llm・happy_path ペルソナで「取り込めたかどうかわからない」

#### 改善 3: PDF 取り込みの進行状態表示
**現状**: Ingest ボタンクリック後、成功/失敗まで UI の変化が乏しい。  
**改善**: ボタンを `disabled + spinner + "取り込み中..."` に即座に変更。完了後に成功バッジをインラインで持続表示（クリアするまで消えない）。  
**根拠**: expert_fast（PDF）20/20 が「成功したかどうか不明」で終了

### 🟡 P2 — 早期対応推奨（ユーザー体験の大幅改善）

#### 改善 4: バリデーションエラーのフォーカス誘導
**現状**: 空欄送信 → エラーメッセージがエリア下部に表示されるが、問題フィールドに自動フォーカスされない。  
**改善**:
```typescript
// バリデーション失敗時
nameInputRef.current?.focus();
nameInputRef.current?.scrollIntoView({ behavior: 'smooth' });
```
**根拠**: novice_validation 60% が回復できない

#### 改善 5: LLM 未設定時のソース取り込みパネル告知
**現状**: LLM バナーが Dashboard 上部に表示されるが、ソース取り込みパネルには告知がない。  
**改善**: LLM 未設定の場合、「Upload source」パネルのヘッダー直下にインフォバー：
```
ℹ️ LLM をまだ設定していません。
  ソースの取り込みはできますが、チャットを有効にするには Settings > LLM が必要です。
  [今すぐ設定する]
```
**根拠**: skip_llm 85% が混乱（取り込みは成功しているのに確認できない）

#### 改善 6: API キーの形式ヒント
**現状**: API キー入力フィールドに形式の説明がない。  
**改善**:
```html
<input placeholder="sk-ant-api03-..." />
<p class="text-xs text-muted">
  Anthropic Console（console.anthropic.com）の API Keys から取得
</p>
```
**根拠**: api_key_wrong_fmt 20 件が誤形式を入力

#### 改善 7: ファイル形式制限の事前表示
**現状**: サポート外のファイル形式は「File upload」クリック後のアップロード時にのみエラー表示。  
**改善**: ファイルドロップ/選択エリアに **受け入れ形式ラベル** を常時表示：
```
📎 CSV または PDF をアップロード
   対応形式: .csv / .pdf (最大 50MB)
```
**根拠**: wrong_file_type ペルソナが正しくブロックされているが、事前に制限を知れれば試行錯誤が減る

### 🟢 P3 — 中長期改善（体験向上）

#### 改善 8: オンボーディングウィザード（初回ログイン）
新規オペレーター向けの 3 ステップウィザード：
1. 「まず LLM API キーを設定しましょう」→ Settings > LLM へ誘導
2. 「コンテンツをアップロードしましょう」→ Upload source へ誘導

## 6. 発見事項の構造的考察

### 「取り込み成功フィードバック」問題の本質

200 ペルソナのうち 73% で発生した「成功メッセージ不可視」は、単なるビジュアルの問題ではなく、**コンポーネントの状態管理とユーザーの認知モデルのギャップ**に起因する。

```
ユーザーの期待: ボタンを押す → 明確に「完了」がわかる
現在の UI   : ボタンを押す → 短時間だけ緑文字が出る → フォームがリセットされる
```

このギャップは、取り込みが成功したかどうかの**信頼性（Trust）** に直結する。
「本当に取り込まれたのか？」という不安はオペレーターの離脱や再試行（重複取り込み）につながる。

### 統合シナリオ vs 単体テストの乖離

単体テスト（`03-ingestion.spec.ts`）では成功するが、フル統合シナリオでは多くが失敗。
この乖離は、**「テストが正しい順序で UI を使う」前提の脆弱性**を示している。

実際のオペレーターは：
1. ログイン後にいろいろな画面を行き来する
2. 設定モーダルを開いては閉じる
3. ブラウザバックや F5 リロードをする
4. 複数タブで操作する可能性もある

現在の IngestionPanel は「新鮮な状態で使われる」前提が強く、**状態の永続性と回復性**を改善する余地がある。
